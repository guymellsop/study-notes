Saved vs runtime state: serialisation and Transient

From THRUST architecture planning · checked against the UE 5.8 engine source · 9 min

In one breath

Every UPROPERTY is saved into its asset by default. That's right for authored data (what a designer sets: "this part uses this data asset") and wrong for runtime state (what happens while playing: "this part has 3 health left"). Transient means "never save this, never load it, and don't copy it when duplicating". It always starts at the class default.

Serialisation in one paragraph

Serialising means turning an object into bytes (to save it to a .uasset, copy it, or send it over the network) and back again. Unreal does it automatically for every UPROPERTY: that's why setting a value in the Details panel and pressing Save just works, and why the reflection system from How Unreal builds your code matters. Specifiers like Transient are how you opt a property out.

// Authored. Saved in the def, copied to every instance.
UPROPERTY(EditDefaultsOnly, Category = "Part Data")
TSoftClassPtr<UDataAsset_VehiclePartInfoBase> PartDataAssetClass;

// Runtime. Never saved, never authorable, reset on every load and every copy.
UPROPERTY(Transient, VisibleInstanceOnly, BlueprintReadOnly, Category = "Part State")
float CurrentHealth = 0.f;
  • VisibleInstanceOnly: shown (read-only) in the Details panel only on a placed instance, not in the class defaults. You can watch the value while playing, but nobody can author it.
  • TSoftClassPtr: a soft reference to a class (the soft version of TSubclassOf). It stores a path and loads nothing until asked. Same reasoning as hard vs soft references and your startup data.

Why a saved runtime field is a problem even if it "works"

In THRUST the part's payload lives in the saved UPDA_CompoundShapeDef, and every craft deep-copies it. If CurrentHealth weren't Transient:

  • It appears in the Details panel, so an author can set it to 3, and every craft built from that def starts damaged.
  • Nothing flags it as wrong. It's not corruption; it's a field that shouldn't exist in the asset at all.

Transient turns a convention ("please don't set that") into a rule the engine enforces.

What exactly gets skipped (from the engine source)

FProperty::ShouldSerializeValue in CoreUObject/Private/UObject/Property.cpp decides, per property, whether an archive writes it:

SpecifierSaved to disk?Copied by duplicate / copy-paste?Use for
(none)YesYesAuthored data
TransientNoNo, reset to defaultRuntime state, caches
DuplicateTransientYesNo, reset to defaultSaved, but unique per copy (e.g. an ID that must not be duplicated)
SaveGame(normal)(normal)Marks a property for save-game archives, which then write only SaveGame-marked properties
  • Duplicating skips Transient too. The archives behind DuplicateObject are flagged persistent, so the same rule applies. For THRUST: deep-copying a def's payload into a craft gives every copy a fresh CurrentHealth at its default, never a stale one.
  • One exception: the flag's own comment says "except for Blueprint CDOs". A Transient property's default set in a Blueprint's Class Defaults is still saved, because the code skips it only when !Ar.IsSerializingDefaults(). So "starts at the default" means the class default, which can come from a Blueprint.

The cost: save games

Transient also means a save file can't capture the value by just serialising the object. If THRUST wants a mid-mission save that remembers damage, you write it deliberately: gather the state into your own save struct (a USaveGame subclass with explicit fields) and restore it on load. That's usually what you want anyway: a save file should record the craft's state, not reach into the shape tree's internals. (Unreal also has the SaveGame specifier plus a save-game archive for "serialise only these fields", but that's the other route, and knowing it exists is enough for now.)

The rule of thumb

Ask: "what should this be in a brand-new craft?" If the answer is "whatever the data says", it's authored. Save it. If it's "the same for every craft, always" (full health, zero heat, not on fire), it's runtime state: Transient.

Quiz yourself

What does "serialise" mean in Unreal?

Convert an object to bytes and back: for saving assets, copying/duplicating, or networking. UPROPERTYs are serialised automatically.

What does Transient do to a UPROPERTY?

It's not saved to disk, not loaded, and not copied when the object is duplicated. It always starts at its class default.

Authored data vs runtime state: one example of each from THRUST.

Authored: PartDataAssetClass (which data asset defines the part). Runtime: CurrentHealth.

If CurrentHealth weren't Transient, what could go wrong?

It'd be an editable, saved field in the def, so an author could set it, and every craft would start with that value. Nothing would flag it.

Transient vs DuplicateTransient?

Transient: not saved and not duplicated. DuplicateTransient: saved to disk, but reset to default whenever the object is duplicated or copy-pasted.

When a THRUST craft deep-copies a def's payload, what's a Transient field's value in the copy?

Its class default. Duplication skips Transient properties, because the duplicate archives are persistent.

What does VisibleInstanceOnly do?

Shows the property read-only on placed instances in the Details panel, but not in class defaults. You can watch it, not author it.

How would THRUST save mid-mission damage if health is Transient?

Deliberately: copy the state into a save struct (a USaveGame subclass with explicit fields) and restore it on load.

The rule of thumb for "Transient or not?"

"What should this be in a brand-new craft?" Whatever the data says means authored. The same for every craft means Transient.
