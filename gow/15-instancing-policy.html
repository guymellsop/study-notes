Ability instancing policy

From class notes · checked against the UE 5.8 engine source · 8 min

In one breath

Instancing policy decides how many ability objects GAS creates. Per Execution: a fresh object every activation, so variables always start clean. Per Actor: one object per character, made when the ability is granted and reused, so variables remember between uses. Non-Instanced: no object at all, and it's deprecated since UE 5.5. In 5.8 it's quietly treated as Per Actor.

Where to find it: the ability's Class Defaults → Advanced → Instancing Policy (the dropdown in your notes), or InstancingPolicy = EGameplayAbilityInstancingPolicy::InstancedPerActor; in a C++ ability's constructor.

Corrections to keep in mind (checked in the engine source)

  • Per Actor creates its instance when the ability is granted, not at the first activation. GiveAbility has the comment "Create the instance at creation time". "Once, up front" is the accurate way to say it.
  • Non-Instanced is deprecated. The enum is marked UE_DEPRECATED_FORGAME(5.5, "Use InstancedPerActor as the default..."), and GetInstancingPolicy() returns Per Actor instead unless the console variable AbilitySystem.Fix.AllowNonInstancedAbilities is set. Older tutorials recommend Non-Instanced for "cheap" abilities; on 5.5+ that advice is out of date.
  • The engine default is Per Execution (set in UGameplayAbility's constructor), which is why your new abilities show "Instanced Per Execution" until you change it.

Which to choose

  • Per Actor for most things: attacks, equip/unequip, anything that runs once at a time per character. Cheaper, and it can cache things. Epic's own recommendation since 5.5.
  • Per Execution when you need overlapping copies (fire a projectile ability again before the first finishes), or when leftover state would be a bug and you'd rather start clean every time.
Per Actor's trap: leftover state

Because the same object is reused, a variable set during one activation is still set at the start of the next. A "combo count" or "has hit something" flag from the last swing leaks into this one. Reset such variables at the start of ActivateAbility (or in EndAbility). Per Execution can't have this bug, which is its main selling point.

In your code

// UWarriorHeroGameplayAbility
TWeakObjectPtr<AWarriorHeroCharacter> CachedWarriorHeroCharacter;

AWarriorHeroCharacter* GetHeroCharacterFromActorInfo()
{
    if (!CachedWarriorHeroCharacter.IsValid())
        CachedWarriorHeroCharacter = Cast<AWarriorHeroCharacter>(CurrentActorInfo->AvatarActor.Get());
    ...
}

This cache (combat components) depends on the instancing policy:

  • Per Actor: the cache is filled once and reused for every activation. That's what it's designed for.
  • Per Execution (the default): each activation is a brand-new object, so the cache starts empty every time. It still works, but it only saves repeated casts within one activation.
  • Non-Instanced (if it were still allowed): the code would write to the shared class default object, so every character would share one cache. The first hero to use it would "win". That's exactly why you can't store state in non-instanced abilities, and part of why Epic removed them.

Worth checking: open GA_Hero_EquipAxe and the other abilities and see which policy they use. If the course sets them to Per Actor, the cache is doing its job. If they're still on the default, now you know what that means.

Quiz yourself

Name the three instancing policies, in one line each.

Per Execution: a new object every activation, state reset. Per Actor: one reused object per actor, state kept. Non-Instanced: no object, runs on the CDO, no state (deprecated).

When is a Per Actor ability's instance created?

When the ability is granted (GiveAbility), not on first activation.

What's the engine's default instancing policy in UE 5.8?

Instanced Per Execution (set in UGameplayAbility's constructor).

What happens to a Non-Instanced ability in UE 5.5+?

It's deprecated. GetInstancingPolicy() treats it as Per Actor unless the AbilitySystem.Fix.AllowNonInstancedAbilities console variable is set.

Can a Per Actor ability be activated while it's already running?

No. Activation is refused, unless "Retrigger Instanced Ability" is on, which ends the running one and starts again.

When would you choose Per Execution over Per Actor?

When several activations must overlap, or when you want guaranteed clean state every time.

What's the classic bug with Per Actor abilities?

Leftover state: variables from the last activation are still set at the start of the next one. Reset them in ActivateAbility or EndAbility.

Why couldn't a Non-Instanced ability safely cache the hero character in a member variable?

It runs on the shared class default object, so every character would read and write the same cache.

Why can't Non-Instanced abilities use Blueprint latent nodes or ability tasks?

Those need an object to hold their state while waiting. Non-Instanced abilities have no instance.
