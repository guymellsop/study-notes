ddx, ddy and the colour boundary mask

From THRUST's cel shader · screen-space derivatives · 8 min

In one breath

The GPU shades pixels in 2×2 blocks, all at once, so each pixel can see its neighbours' values. ddx(v) is "my right-hand neighbour's v minus mine"; ddy(v) is the same vertically. In a flat area of colour that's 0; where two colours meet, it spikes. The spike is the boundary.

The code

// boundary registers as a spike in the gradient. Max-of-channels rather
// than luminance: two colours of equal brightness still form a boundary.
float3 dX = ddx(BaseColor);
float3 dY = ddy(BaseColor);

float gx = max(abs(dX.r), max(abs(dX.g), abs(dX.b)));
float gy = max(abs(dY.r), max(abs(dY.g), abs(dY.b)));

float g = max(gx, gy);
return saturate(g * Width);

Why the GPU can do this: quads

  ┌─────┬─────┐
  │  A  │  B  │    One quad: four pixels shaded together, in lockstep.
  ├─────┼─────┤    ddx at A = value(B) − value(A)
  │  C  │  D  │    ddy at A = value(C) − value(A)
  └─────┴─────┘

Pixels are never shaded alone. The hardware always runs them in 2×2 quads, the same shader in step, so "what did my neighbour get for this variable?" is basically free. The GPU needs this anyway for texture mipmapping: how fast UVs change across the screen decides which mip level to sample. ddx/ddy just let you use the same trick on any value.

The name: these are partial derivatives (rates of change) in screen x and y. In Unreal's material editor they're the DDX and DDY nodes.

How the snippet turns that into an edge mask

 red  red | blue blue
 red  red | blue blue
   ddx in the red area:   red − red  = 0     → no edge
   ddx across the line:   blue − red = large → edge
  1. ddx/ddy of the colour: per channel, how much it changes to the next pixel, horizontally and vertically.
  2. abs: red→blue and blue→red are the same edge. Drop the sign.
  3. max over r, g, b: use whichever channel changed most. A luminance (brightness) comparison would miss two colours of equal brightness, like a pure red and a green of the same lightness. That's what the comment means.
  4. max(gx, gy): an edge in either direction counts.
  5. saturate(g * Width): Width is really a sensitivity/gain: the bigger it is, the smaller a colour change needed to read as a full edge. saturate clamps to 0–1.

The limits (where it surprises you)

  • Lines are about 1–2 pixels thick, always. Derivatives only compare immediate neighbours, so Width cannot make the line thicker; it only makes faint edges stronger. Thicker or consistent outlines need sampling further away, usually in a post-process that reads scene colour, depth or a custom stencil at several offsets.
  • It can miss edges. The comparison only happens inside a quad. A boundary that falls exactly between two quads (pixel 1 red, pixel 2 blue, but they're in different quads) gives 0 in both. The result: lines with gaps or a dotted look, especially on edges that line up with the pixel grid.
  • Coarse vs fine. HLSL has ddx_coarse (one value shared across the quad) and ddx_fine (per pixel row/column). Plain ddx is allowed to be the coarse one, which makes edges a little blockier.
  • Gradients light up. A smooth fade changes a little every pixel. Small, but non-zero, so with a high Width the whole gradient reads as "edge". Hard-edged colour areas work best.
  • It's screen-space. The same boundary gives the same ~1 pixel line near or far; it doesn't scale with distance.
  • Pixel shader only. Vertex shaders don't run in quads, so there are no neighbours to compare.

Quiz yourself

What does ddx(v) return?

How much v changes from this pixel to its horizontal neighbour: the neighbour's value minus this one.

Why can a pixel shader know its neighbour's value at all?

The GPU shades pixels in 2×2 quads in lockstep, so the values of the other three pixels are available.

What does the GPU normally use derivatives for, even if you never call ddx?

Choosing texture mip levels: how fast UVs change across the screen.

Why max of the r, g, b differences instead of comparing luminance?

Two different colours of the same brightness have equal luminance, so a greyscale comparison sees no edge. Per-channel comparison catches it.

Does raising Width make the lines thicker?

No. It's a sensitivity multiplier. Line thickness is fixed at about 1–2 pixels by the neighbour comparison.

Why can derivative edge detection leave gaps in a line?

Differences are only computed inside each 2×2 quad. A boundary exactly between two quads is invisible to both.

Why might a smooth colour gradient show up in the edge mask?

It changes a little every pixel, so derivatives are small but non-zero, and a high Width amplifies them into "edge".

How would you get thicker, more reliable outlines?

A post-process that samples scene colour, depth or custom stencil at several pixel offsets, instead of relying on 2×2 derivatives.
